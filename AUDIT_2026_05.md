## 0. Executive summary

F33D3R is **architecturally honest and unusually disciplined**. Brain isolation is real (CI-enforced), PIAL identity is the right primitive, the 2.5% creator fee is plausible at scale, and the AETHYR_FABRIC_SPEC is the kind of document most pre-Series-A teams never write. The codebase is roughly 70% of an enterprise platform. The remaining 30% is the part that actually ships.

The critical truth: **the platform is not yet usable for adult creators at the standard you've set**. Three structural problems make this so:

1. **Adult-content gating is cosmetic, not architectural.** `is_nsfw` blurs an image with CSS but the URL is served to every user. A 13-year-old with developer tools defeats it in five seconds. Pillar 6 (safe by architecture) is currently a wish.
2. **The CSAM pipeline is wrong, not just incomplete.** F33D3R is calling Azure Content Moderator's *adult* classifier and treating a score > 0.9 as CSAM. That means a legitimate Verity-tier-2 creator who posts adult content gets her PIAL terminated and reported to NCMEC CyberTipline. This is a severe defect — wrongful CSAM reports are a federal-level platform-killing event.
3. **Vovin messaging breaks on every new device.** Identity keys are device-local; a new device = a new key = "encrypted for another session" failures. Users will hate it within a week.

The strongest parts: AethyrRank's 7-stage pipeline, Verity's privacy-preserving decision-hash design, Ain Soph's double-entry rigour, the Berserker design system's coherence. None of these need to be rewritten.

The order of operations is therefore not "fix everything" but **stop the bleeding first** (server-side NSFW gating, CSAM logic correction, Vovin device key consistency), then **complete the partnership-readiness work** (Ripple inspection, Stripe SFW pay rails), then **close the experience gaps** (dwell-time signals, music queue, video transcoding).

## 1. Architecture posture

The 14-brain split is justified, not over-engineered:

- **One DB per brain** is enforced at CI time. Cross-brain reads at the SQL layer are blocked by `enforcement/` validators. That's already better than 90% of platforms at this scale.
- **PIAL UUID as the only cross-brain identity** is the right call. It survives bans, handle changes, and policy shifts. Every other internal ID is opaque to the rest of the system.
- **Nantar as the only edge brain** is correct — gateway pattern, not service-mesh-anywhere chaos.
- **Zodacare advises, Elohim Veni enforces** — the deterministic rule ladder in `elohim-veni/src/decision.rs` is exactly the kind of code regulators want to read. No ML in the enforcement path. Reproducible from inputs.
- **Schema Registry + event taxonomy** in `events/schemas/` is more contract discipline than most Series B teams have.

What's not present yet (per `AETHYR_FABRIC_SPEC.md` §10):

- Ed25519-signed Glyph packets — currently identity is DB-only, not cryptographically anchored to a device key.
- Karma routing engine — tables exist, no compute.
- Per-event nonce on AET transfers — idempotency key only.
- Multi-device PIAL key bundle.

These are all on the V2/V3 roadmap. None of them block today's user-facing features.

### Documentation drift to fix

`README.md` says "PostgreSQL 16"; `docker-compose.local.yml` uses `postgres:18-alpine`; `CLAUDE.md` says minimum 18. Pick one and propagate. Compose is correct.

## 2. Domain audits

### 2.1 Media pipeline & NSFW gating

**Current state.** Caeor handles images well (multi-size WebP derivatives, Lanczos3, sensible naming). For video it does pass-through only — no transcoding, no HLS/DASH, no thumbnail extraction. A `transcoding` brain is referenced in `feed-engine/internal/config/config.go:38` and exists in compose under a different name (port 8098 in some references) but **is never invoked from Nantar's upload path**. Videos are stored as the original mp4/mov/webm.

**The cosmetic-blur defect.** In `feed_items.html:62`:

```go
{{if and $p.IsNSFW (eq $.User.ContentSetting "safe_mode")}}
  <div style="filter:blur(20px);…">…</div>
{{end}}
```

A user without `safe_mode` receives the original image URL in HTML, no blur, no auth check. A user *with* `safe_mode` receives a blurred view but the URL is still in `<img src>` — `Inspect → remove filter` defeats it in a single click. The media path (`/static/media/...`) is also served by Nantar with no PIAL or capability check (`feed-engine/internal/handler/media.go` only handles uploads, not serving). So curl works equally well.

**The CSAM defect.** In `feed-engine/internal/handler/compliance.go:336–411`:

```go
flagged := cmResult.IsImageAdultClassified && score > 0.9
```

This treats an Azure Content Moderator *adult* classification as CSAM. An adult creator's legitimate post gets her PIAL terminated, capabilities revoked, and an entry inserted into `law_enforcement_queue` with `report_type='csam'`. Independently, `verity/src/main.rs:645` has a parallel CSAM endpoint stubbed to always return `clean`. So:

- A real CSAM upload through Verity's path: not detected.
- A legitimate adult upload through compliance.go's path: false-flagged as CSAM.

This is the #1 ship blocker.

**2257 records** in Verity are well-designed structurally — `statement_hash = SHA-256(pial_id|age_band|ts|document_hash)`, gov_id KYC required, kyc_submission_id linked. But:
- It's one record per *creator*, not per *scene with depicted persons*. 18 USC 2257 requires per-scene records identifying every depicted performer. Single-creator content (the OnlyFans pattern) is fine; collab content is not compliant.
- The Nantar→Verity call is fire-and-forget (`compliance.go:306`) with no receipt tracking. If the call drops, the post still publishes.

**DMCA** stores requests with no SLA, no counter-notice flow, no creator notification, no automatic content suspension during dispute.

**Top fixes.** P0 — server-side NSFW URL gating + correct CSAM logic + integrate transcoder. P1 — PhotoDNA hash matching + per-scene 2257. P2 — DMCA SLA + counter-notice. Detailed scope in §4.

### 2.2 AethyrRank

**Strong skeleton, missing meat.** The 7-stage pipeline is fully implemented: pre-rank → neural → AESQ → safety barrier → velocity → revenue → re-rank. LinUCB exploration is real, checkpointed every 60s to `linucb_checkpoints` in Postgres, restored on restart. AESQ scoring (Alignment / Expansion / Shadow / Quality / Freshness) has actual math behind it, not labels. Safety barrier removes items hard, never soft-penalises. The clean separation of inference (Jung/AESQ) from enforcement (Elohim Veni) is exactly what `ARCHITECTURE.md §2.4` promises.

**Two ranking-quality gaps that matter.**

1. **Dwell-time / scroll signals are absent end-to-end.** `feedback_events.dwell_ms` exists in the schema, training data extraction expects it, and AethyrRank's neural stub reserves a feature for it — but the Nantar frontend never populates it. No scroll-pause tracking, no completion %, no time-to-interaction. This is *the* primary signal at ByteDance. Without it, AethyrRank is a like-counter.
2. **The neural stage is a heuristic stub.** `aethyrrank-engine/src/pipeline/neural.rs` blends 7 features with hardcoded weights. There's a `training/` directory with a Wide-and-Deep PyTorch script, but no model is loaded at runtime, no ONNX export, no inference framework wired in.

**Cold start, exploration, diversity.** Per-surface LinUCB (not per-user) — fine for now, becomes a bottleneck north of ~100k DAU. UCB with a fixed alpha, not Thompson sampling. Diversity is creator-spacing only — no topic balance, no engagement-bait suppression, no anti-clustering.

**Top fixes.** P0 — instrument dwell_ms + scroll depth in Nantar frontend, send to AethyrRank `/feedback`. P0 — train and deploy real neural model (the training pipeline exists, finish it). P1 — Thompson sampling + per-user state. P1 — topic-level diversity quotas.

### 2.3 Vovin messaging

The user said: *"when users sign out or change devices etc it messes with keys."* This is real and structural, not a bug.

**Architecture.** Server stores ciphertext + IVs only — correct. WebSocket push for real-time. Ratchet sessions stored as encrypted blobs server-side that the relay cannot decrypt — also correct. X3DH (`x3dh.rs`) and Double Ratchet (`ratchet.rs`) are fully implemented in Rust, but `#[allow(dead_code)]`. They are not on the live message path.

**The actual live path is V1 ECDH-only.** No DH ratchet step per message — symmetric chain KDF only. Compromise of a chain key reveals all forward messages until the next session re-init. This is below Signal's forward-secrecy floor.

**The device-key problem.** Identity keypair is generated client-side and stored in IndexedDB namespaced `vovin_v1_<PIAL_UUID>`. Behaviour by scenario:

- Sign out, sign back in, same browser: keys persist (IDB survives logout). Works correctly.
- Sign in on a new device: new keypair generated. Old conversations cannot be decrypted. Other senders' ratchets break.
- Clear browser data: silent total data loss. No recovery.
- Incognito: ephemeral keys, broken on tab close.
- Two tabs open: race condition writing to `ratchet_<pialId>`.

The protocol does theoretically support multi-device — `/v1/devices` lets a PIAL register N public keys — and senders fan out N ciphertexts. But there is no master-key + per-device-derived-key scheme, so device A and device B are independent identities the world has to track. There's no key backup, no recovery code, no Sesame-style linked devices.

**Metadata.** No sealed sender. Vovin sees full sender→recipient PIAL graph in the clear. Conversation graph is observable to anyone with DB access.

**Top fixes.** P0 — PIAL master identity key + per-device derived keys + recovery passphrase / mnemonic. P0 — wire the existing X3DH + full Double Ratchet into the live path (they're already written, just not connected). P1 — sealed sender. P1 — encrypted server backup of ratchet state with client-only-decryption.

### 2.4 Zior music

**Audio analysis is genuinely impressive.** Symphonia decoding, FFT + onset detection for BPM (40–220), Krumhansl-Schmuckler key/mode, RMS energy, spectral flux, band energies, vocal heuristic. Maps into the 8-axis psychological space that AethyrRank uses for content ranking — same latent space as user vectors, dot product = alignment. Internal-only naming respected.

**Playback UX is the gap.** A persistent bottom-bar player exists and works, but:

- **No queue.** Playing a track stops at the end. No "play next." No auto-advance.
- **No background play.** Page navigation pauses audio. No Media Session API, no lockscreen controls.
- **No persisted playback state.** Refresh = lose your place.
- **No HLS/DASH.** Plain HTTP range requests. One bitrate.
- **No history table.** `tracks.play_count` is aggregated; per-user listening history doesn't exist as a record. AethyrRank can't learn from it.
- No playlists. No equalizer. No lyrics. No radio. No download.

You can't compete with SoundCloud or Apple Music until at minimum: queue, autoplay-next, persistent state across navigation, Media Session API.

### 2.5 AET ledger + payments

**Ain Soph (wallet ledger) is sound at the row level.** Double-entry pairs, BIGINT µAET (no float), `balance >= 0` CHECK, idempotency via UNIQUE on `idempotency_key`, `SELECT FOR UPDATE` on sender during transfer, append-only `ledger_entries`. The 2.5% / 3% / 1% fee schedule is consistent with `AETHYR_FABRIC_SPEC.md §5.2`.

**Two issues.**

1. Default isolation is READ COMMITTED, not SERIALIZABLE. Two concurrent transfers from the same account to different recipients are vulnerable to read-skew. Probability of hitting it is low at current load; probability becomes meaningful as concurrency rises. One-line fix.
2. Documentation drift: `ain-soph/README.md:108` claims transfer fee is 0%; the code charges 3%. Pick one and propagate.

**Aethyr Ledger is partially present.** A 2-second sealer task runs and writes hash-chained blocks (SHA-256, prev_hash linkage, block_hash field). But:

- `events_root` is a flat hash-fold of event IDs, not a Merkle tree. A third party (Ripple) cannot verify a single transaction's inclusion without fetching the entire block.
- **Ain Soph and Aethyr Ledger are not synchronised.** A transfer in Ain Soph is not automatically recorded in Aethyr Ledger blocks. The two ledgers are independent. There's no documented data flow Ain Soph → Aethyr Ledger. So Aethyr Ledger blocks are likely empty or testing-only in practice.
- `glyph_sig` field exists on `ledger_events` but is not validated server-side. Anyone with DB write access can insert a fake signature.

**Ripple inspection-readiness gaps.**

- ✅ Append-only journal, double-entry, idempotency
- ⚠ Hash chain (yes, but no Merkle proofs)
- ❌ Reserve attestation (no proof platform liability ≤ reserves)
- ❌ AML/KYT screening on transfers (Verity exists; not called by Ain Soph)
- ❌ Travel Rule data (originator+beneficiary for >$1k transfers)
- ❌ Cold/hot wallet separation
- ❌ Reproducible state from genesis (no replay tool)
- ❌ Ed25519 signature validation on settlement
- ❌ Incident rollback procedure

**Stripe integration: not started.** No code. The integration plan for SFW rails: Thessalon `/v1/onramp/stripe`, webhook endpoint with HMAC-SHA256 signature verification, Stripe Connect Express for creator payouts, 3DS automatic, Idempotency-Key passthrough, Stripe Tax. Adult content **must use a different processor** (CCBill / Segpay / Epoch) — Stripe's TOS forbids adult. This is a hard constraint and dictates a two-rail design in Thessalon (`payment_rail: 'stripe'|'ccbill'`).

### 2.6 Identity, KYC, compliance

**Verity is well-designed.** Decision-hash architecture stores no PII — just `SHA-256(pial_id|status|age_band|tier|ts)`. Document hashes are stored, document images never reach Verity. 4-tier model is documented and enforced (`models.rs:179–183`). `decide()` endpoint returns reproducible status given the same inputs. Risk profile is composite (IP rep, velocity, failed KYC, duplicate detection, device count) — this is exactly the right shape.

**Elohim Veni's decision ladder is the cleanest code in the repo.** Ten rules, deterministic, no ML. Every outcome reproducible from the audit log. This is the kind of code regulators ask for and rarely get.

**The big gap is at the seam.** Two CSAM endpoints (compliance.go and verity), neither correct: the first false-flags adult content, the second is a stub. Caeor doesn't compute file hashes on upload, so the compliance flow has no input to feed an actual PhotoDNA query. The 2257 record creation is fire-and-forget. Data deletion requests are persisted but no consumer process actually deletes anything.

**PIAL bootstrap is synchronous on signup (correct), but PIAL is a UUID, not yet a cryptographic anchor.** `AETHYR_FABRIC_SPEC §10` knows this — Ed25519 PIAL signing is V1-incomplete, V3 deliverable. Until then, "identity you own forever" means "identity you own as long as our DB is honest", which is weaker than the marketing.

### 2.7 UI/UX

The Berserker design system is **coherent and visually confident** — 6 accent themes, dark mode via `[data-mode="dark"]`, sensible CSS variables, two button variants, a unified modal/overlay system with semantic opacity scaling. The dual `.pcd` (desktop card) / `.pcf` (mobile focus, TikTok-like) pattern is sophisticated and works.

**Real accessibility debt.** No `prefers-reduced-motion` media query — animations run unconditionally (WCAG 2.3.3 fail). Sparse `:focus-visible` styles. Many interactive `<div>`s without keyboard handlers. ARIA labels missing on icon buttons. `text-muted` at 20% opacity is right at the AA contrast floor. Modals don't trap focus. None of this is hard to fix; it's just been deferred.

**Cross-page inconsistencies.** Theme selector lives on both `/profile` and `/settings`. Empty states are ad-hoc per template. No unified error banner. Light-mode styles `.post-card` differently from dark-mode (intentional, but undocumented).

**Mobile.** The full-screen TikTok layout works on `<1024px`. Tap targets ≥44px in most places. Safe-area-inset-bottom used. `/messages` sidebar at 280px fixed is cramped on small phones.
